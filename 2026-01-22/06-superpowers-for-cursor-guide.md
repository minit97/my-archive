# Superpowers for Cursor - AI 코딩 에이전트 워크플로우 가이드

> **경로**: `/superpower-study/superpowers-for-cursor`  
> **유형**: Cursor 확장 스킬셋  
> **원본**: [Superpowers by obra](https://github.com/obra/superpowers)

---

## 요약

**Superpowers**는 AI 코딩 에이전트가 체계적으로 소프트웨어를 개발하도록 강제하는 워크플로우입니다. 원래 Claude Code용으로 만들어졌으며, 이 버전은 **Cursor에서 사용할 수 있도록 변환**한 것입니다.

### 왜 필요한가?

| 문제 (기존) | 해결 (Superpowers) |
|------------|-------------------|
| AI가 요청하면 바로 코드 작성 | 설계부터 검토 후 코드 작성 |
| 설계 없이 구현 → 대규모 수정 | 브레인스토밍 → 계획 → 실행 |
| "됐습니다" 했는데 테스트 안 돌아감 | 검증 없이 완료 주장 금지 |
| 버그 수정 시 추측으로 시도 | 근본 원인 파악 후 수정 |

---

## 핵심 원칙 (4대 철칙)

```
┌─────────────────────────────────────────────────────────────┐
│  1. Evidence over Claims: 검증 없이 완료 주장 금지           │
│  2. Test-First: 테스트 전에 코드 작성 금지                   │
│  3. Root Cause First: 원인 파악 전 수정 금지                 │
│  4. YAGNI: 필요한 것만 구현                                  │
└─────────────────────────────────────────────────────────────┘
```

### 2단계: User Rules 설정

`Cursor Settings (⌘+,) → Rules → User Rules`에 추가:

```markdown
# SUPERPOWERS 활성화

모든 작업에서 ~/.cursor/superpowers/ 폴더의 스킬들을 참조하고 따르라.

## 스킬 사용 규칙
1. 작업 시작 전 관련 스킬이 있는지 확인
2. 스킬이 있으면 반드시 해당 스킬을 따라야 함
3. 스킬 사용 시 "~/.cursor/superpowers/XX-스킬명.md 스킬을 사용합니다" 선언
4. 스킬의 체크리스트가 있으면 TodoWrite로 추적

## 핵심 워크플로우
- 코드 작성 전 → 01-brainstorming.md
- 설계 승인 후 → 02-writing-plans.md
- 계획 실행 시 → 03-executing-plans.md
- 구현 중 항상 → 04-tdd.md
- 버그/실패 시 → 05-systematic-debugging.md
- 완료 선언 전 → 06-verification.md

## 철칙
- Evidence over Claims: 검증 없이 완료 주장 금지
- Test-First: 테스트 전에 코드 작성 금지
- Root Cause First: 원인 파악 전 수정 금지
- YAGNI: 불필요한 기능 금지
```

## 스킬 상세 설명

### 01. Brainstorming (브레인스토밍)

**목적**: 코드 작성 전 설계 검토

**프로세스**:
1. 프로젝트 상태 파악 (파일, 문서, 최근 커밋)
2. **한 번에 하나씩** 질문으로 아이디어 정제
3. 2-3개 접근법 제시 + 장단점 비교
4. 설계를 200-300단어 섹션으로 나눠서 제시
5. 각 섹션마다 확인
6. 승인 후 `docs/plans/YYYY-MM-DD-<topic>-design.md`에 저장

**절대 금지**:
- 설계 승인 전 코드 작성
- 한 번에 여러 질문
- 대안 없이 하나만 제시

---

### 04. TDD (테스트 주도 개발)

**Iron Law**:
```
┌─────────────────────────────────────────────────────────────┐
│     실패하는 테스트 없이 프로덕션 코드 작성 금지            │
└─────────────────────────────────────────────────────────────┘
```

**Red-Green-Refactor 사이클**:

```
    ┌──────────────┐
    │    RED       │  ← 실패하는 테스트 작성
    └──────┬───────┘
           ↓
    ┌──────────────┐
    │ VERIFY RED   │  ← 실패 확인 (필수!)
    └──────┬───────┘
           ↓
    ┌──────────────┐
    │   GREEN      │  ← 최소 코드로 통과
    └──────┬───────┘
           ↓
    ┌──────────────┐
    │ VERIFY GREEN │  ← 통과 확인 (필수!)
    └──────┬───────┘
           ↓
    ┌──────────────┐
    │  REFACTOR    │  ← 정리 (green 유지)
    └──────────────┘
```

**테스트 전에 코드 작성했다면?**
- 삭제
- "참고용"으로 남기지 말 것
- **삭제는 진짜 삭제**

---

### 05. Systematic Debugging (체계적 디버깅)

**Iron Law**:
```
┌─────────────────────────────────────────────────────────────┐
│        근본 원인 조사 없이 수정 금지                        │
└─────────────────────────────────────────────────────────────┘
```

**4단계 프로세스**:

| Phase | 핵심 활동 | 성공 기준 |
|-------|----------|----------|
| **1. 근본 원인** | 에러 읽기, 재현, 변경 확인, 증거 수집 | 뭐가 왜인지 이해 |
| **2. 패턴** | 작동 예시 찾기, 비교 | 차이점 파악 |
| **3. 가설** | 이론 수립, 최소 테스트 | 확인되거나 새 가설 |
| **4. 구현** | 테스트 생성, 수정, 검증 | 버그 해결, 테스트 통과 |

**3번 이상 수정 실패?** → 아키텍처 의심, 4번째 수정 시도 금지

## 실제 사용 예시

### 새 기능 개발

```
1. /brainstorm
   → AI가 질문으로 요구사항 정제
   → 2-3개 접근법 제시
   → 설계 문서 작성

2. /plan  
   → bite-sized 태스크로 분해
   → 각 태스크에 테스트, 코드, 검증 포함
   → docs/plans/에 계획 저장

3. /execute
   → 배치 단위로 실행 (기본 3개 태스크)
   → 각 배치 후 피드백 대기
   → 막히면 즉시 질문

4. /verify
   → 테스트 실행
   → 출력 확인 후 완료 선언
```

### 버그 수정

```
1. /debug
   → 에러 메시지 분석
   → 재현 확인
   → 근본 원인 추적
   → 가설 수립 및 테스트

2. /tdd
   → 버그 재현하는 실패 테스트 작성
   → 최소 수정으로 통과
   
3. /verify
   → 전체 테스트 실행
   → 출력 확인 후 완료 선언
```

## 절대 금지되는 합리화

| 변명 | 현실 |
|------|------|
| "이건 간단해서 스킬 필요 없음" | 틀림. 스킬 확인. |
| "스킬이 과한 것 같음" | 틀림. 스킬은 존재 이유가 있음. |
| "기억나니까 다시 안 읽어도 됨" | 틀림. 스킬은 진화함. 다시 읽어. |
| "일단 먼저 해보고" | 틀림. 스킬 먼저 확인. |
| "너무 단순해서 테스트 불필요" | 단순한 코드도 깨짐. 테스트 30초. |
| "나중에 테스트" | 바로 통과하는 테스트는 아무것도 증명 못 함. |
| "급해서 프로세스 시간 없음" | 체계적 디버깅이 추측 삽질보다 빠름. |

## 핵심 포인트

- 🎯 **체계적 워크플로우**: 브레인스토밍 → 계획 → TDD → 검증
- 🧪 **TDD 강제**: 테스트 먼저, 예외 없음
- 🔍 **근본 원인 우선**: 추측 수정 금지
- ✅ **검증 필수**: "됐습니다" 전에 증거 확보
- 📋 **YAGNI**: 필요한 것만 구현
