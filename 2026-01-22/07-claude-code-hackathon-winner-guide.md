## 1. Skills, Hooks, Subagents의 구조적 분업

### 3계층 자동화 시스템

```
┌─────────────────────────────────────────────────────────────┐
│  Layer 1: Skills & Commands                                 │
│  → 무엇을 할지 정의 (명시적 호출)                            │
├─────────────────────────────────────────────────────────────┤
│  Layer 2: Hooks                                             │
│  → 언제 할지 정의 (이벤트 기반 자동 반응)                    │
├─────────────────────────────────────────────────────────────┤
│  Layer 3: Subagents                                         │
│  → 누가 할지 정의 (역할 분리 및 위임)                        │
└─────────────────────────────────────────────────────────────┘
```

### Layer 1: Skills & Commands

| 구분 | 위치 | 역할 | 특징 |
|------|------|------|------|
| **Skills** | `~/.claude/skills/` | 워크플로우 정의 | 광범위한 지침 (코딩 표준, TDD, 보안 리뷰) |
| **Commands** | `~/.claude/commands/` | 슬래시 명령 | 구체적인 실행 진입점 (`/refactor-clean`) |

**체이닝 가능**: `/tdd` + `/e2e` + `/test-coverage` 연결하여 복합 워크플로우 구성

### Layer 2: Hooks

이벤트에 **자동으로 반응**하는 레이어

| Hook | 트리거 시점 | 예시 |
|------|-------------|------|
| **PreToolUse** | 도구 실행 전 | npm/yarn/pytest 감지 시 tmux 세션 권고 |
| **PostToolUse** | 도구 실행 후 | TS 파일 수정 시 자동 Prettier + tsc + console.log 경고 |
| **Stop** | Claude 응답 완료 시 | 수정된 파일들의 console.log 최종 감사 |

**핵심**: 개발자가 매번 "포맷팅해줘", "타입 체크해줘" 요청 불필요

### Layer 3: Subagents

역할별 **전문 에이전트**에게 위임

| Subagent | 역할 |
|----------|------|
| `planner.md` | 기능 구현 계획 수립 |
| `architect.md` | 시스템 설계 결정 |
| `code-reviewer.md` | 품질 리뷰 |
| `security-reviewer.md` | 취약점 분석 |

**핵심 이점**: 
- 각 Subagent는 **제한된 도구/MCP 권한**만 가짐
- 메인 Claude의 **컨텍스트 윈도우 보존**

### 3계층 협업 예시: 리팩토링

```
1. Skills에 리팩토링 원칙 정의
   (모듈화 우선, 메가 파일 지양, 죽은 코드 제거)
        ↓
2. /refactor-clean 명령 실행
        ↓
3. PostToolUse 훅이 자동 포맷팅 + 타입 체크
        ↓
4. refactor-cleaner.md Subagent에 실제 작업 위임
        ↓
5. 메인 에이전트는 전체 진행 관리에 집중
```

## 2. 컨텍스트 경제학 — 도구가 많을수록 성능이 떨어진다

### 컨텍스트 윈도우의 실제

| 항목 | 수치 |
|------|------|
| 스펙상 컨텍스트 | 200k 토큰 |
| MCP/플러그인 활성화 시 | **70k까지 감소** |
| 간극 | 130k 토큰 |

**원인**: 각 도구가 활성화될 때마다 **도구 정의와 사용법**이 컨텍스트에 올라감

> 최근 패치로 MCP가 lazy loading으로 변경되어 개선됨

### 경험적 규칙

```
┌─────────────────────────────────────────────────────────────┐
│  "20-30개 설정, 10개 미만 활성화, 80개 미만 도구"            │
└─────────────────────────────────────────────────────────────┘
```

| 항목 | 등록 | 실제 활성화 |
|------|------|------------|
| MCP | 14개 | 5-6개 |
| 플러그인 | 다수 | 4-5개 |

### 왜 중요한가?

**컨텍스트 = Claude의 작업 기억**

| 컨텍스트 부족 시 발생하는 문제 |
|------------------------------|
| 20분 전 설계 결정을 잊어버림 |
| 일관성 없는 코드 생성 |
| 같은 질문을 반복해야 함 |
| 도구 선택에 인지 자원 분산 |

**역설**: 기능 확장 → 성능 저하

### 해법

> "기능을 최대한 켜는 게 아니라, **지금 이 작업에 정확히 필요한 도구만** 켜고 나머지는 꺼두는 것"

## 3. 분리가 병렬성을 만든다 — Fork, Worktree, Subagent

### 핵심 원리

```
병렬성의 본질 = 분리의 문제

먼저 나누고 → 그 다음 동시에
```

### 3가지 병렬화 기법

| 기법 | 분리 단위 | 사용 시나리오 |
|------|----------|--------------|
| **/fork** | 대화 세션 | 백엔드 API + 프론트엔드 동시 개발 |
| **Git Worktrees** | 파일 시스템 | 완전히 독립된 브랜치 작업 |
| **Subagents** | 역할과 권한 | 보안 리뷰 + 코드 리뷰 병렬 실행 |

### /fork — 대화 세션 분리

```bash
# 현재 대화를 복제하여 별도 세션으로 분기
/fork
```

- 원래 세션: 백엔드 API 개발 계속
- 분기 세션: 프론트엔드 컴포넌트 작업

**주의**: **비중첩(non-overlapping) 작업**에서만 효과적

### Git Worktrees — 파일 시스템 분리

```bash
git worktree add ../feature-branch feature-branch
```

- 완전히 독립적인 디렉토리 생성
- 각 Worktree에서 별도 Claude 인스턴스 실행
- **충돌 불가능** 상태를 구조적으로 보장

### Subagents — 역할 분리

```
메인 Claude: "보안 리뷰 해줘"
    ↓
security-reviewer Subagent가 백그라운드 작업
    ↓
메인 Claude는 다른 작업 계속 진행
    ↓
결과 받아서 통합
```

**설계 원칙**: 각 Subagent는 **제한된 도구/MCP 권한**만 보유

### 공통 원리

```
/fork      → 대화 세션 분리
Worktrees  → 파일 시스템 분리  
Subagents  → 역할과 권한 분리

↓ 모두 같은 패턴 ↓

"먼저 나누고, 그 다음 동시에"
```

이 원리는 Claude Code를 넘어 일반적 시스템 설계에도 적용:
- 마이크로서비스 아키텍처
- 데이터베이스 샤딩
- 기능 단위 팀 구성

## 핵심 포인트

1. **3계층 자동화**: Skills(무엇을) + Hooks(언제) + Subagents(누가)
2. **컨텍스트 경제학**: 도구를 많이 켜면 실제 사용 가능한 컨텍스트가 줄어듦
3. **선택적 활성화**: 20-30개 설정, 10개 미만 활성화
4. **분리 → 병렬**: 범위를 먼저 나누면 동시 실행이 자연스럽게 가능
5. **병렬화 3기법**: /fork(세션), Worktrees(파일), Subagents(역할)

## 인용

> "자동화를 도구로 보면 '이 도구가 저 작업을 빠르게 해준다'에서 사고가 멈춘다. 자동화를 계층으로 보면 '이 작업 전체를 어떻게 구조화할 것인가'로 질문이 확장된다."

> "컨텍스트는 희소 자원이고, 희소 자원의 관리가 시스템 성능을 결정한다."

> "병렬성은 속도의 문제처럼 보이지만, 본질은 분리의 문제다."
