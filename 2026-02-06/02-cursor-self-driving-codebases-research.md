## 요약

Cursor 연구팀이 **수천 개 AI 에이전트를 동시에** 돌려, 사람 개입 없이 **일주일 동안** 웹 브라우저의 코드 대부분을 완성하는 실험을 공개했습니다. 시스템은 **~1,000 커밋/시간**, 1주일간 **1,000만 tool call**을 달성했으며, 한 번 시작하면 사람의 개입 없이 코드가 계속 수렴했다는 점이 핵심입니다.

> "코드가 스스로 진화하는 단계에 들어섰습니다"

---

## 연구 배경

### 프로젝트: 웹 브라우저 구현

```
왜 브라우저인가?
├── 충분히 복잡해서 프론티어 모델의 한계 드러남
├── 다양한 서브시스템이 협업해야 함
└── 벤치마크로 적합
```

### 초기 시도와 실패

| 단계 | 접근법 | 결과 |
|------|--------|------|
| **1차** | Opus 4.5에게 전체 계획 요청 | 맥락 상실, 조기 성공 선언, 복잡성에 막힘 |
| **2차** | 의존성 그래프 + 수동 에이전트 스폰 | 처리량 증가, but 에이전트 간 소통 불가 |
| **3차** | GPT-5.1/5.2로 전환 | 지시 정확도 향상, 단일 에이전트로는 느림 |

> **핵심 질문**: "컴퓨팅에 10배 투자하면 10배 의미있는 처리량을 얻을 수 있을까?"

## 시스템 진화 과정 (5단계)

### 1단계: 자율 조율 (Self-coordination) - 실패

```
Agent 1 ──┐
Agent 2 ──┼──→ 공유 상태 파일 (shared state file)
Agent 3 ──┘

문제:
- 락을 너무 오래 잡음, 해제 안 함
- 20개 에이전트 → 1~3개 수준의 처리량
- 큰 작업 회피, 안전한 작은 변경만 선택
```

### 2단계: 역할 분리 (Structured Roles) - 개선

```
Planner → Executor → Workers → Judge
(계획)     (실행)     (작업)    (판정)

개선: 단일 책임자가 실행 소유
문제: 가장 느린 Worker가 병목
```

### 3단계: 연속 실행기 (Continuous Executor) - 유연해짐

```
┌──→ Executor (계획 + 실행 + 스폰) ──→ Workers ──┐
│                                                   │
└──────────────── 무한 루프 ────────────────────────┘

신선도 유지 메커니즘:
- scratchpad.md 수시 재작성 (추가 X)
- 컨텍스트 한계 시 자동 요약
- 자기 성찰 + 정렬 리마인더
- 언제든 방향 전환 권장
```

**문제**: 너무 많은 역할 동시 수행 → 병리적 행동 (랜덤 슬립, 조기 완료 선언, 직접 코딩)

### 4단계: 최종 설계 - 재귀적 Planner + Worker

```
┌─────────────────────────────────────────────────────────────┐
│  Root Planner (전체 범위 소유, 코딩 안 함)                   │
│       │                                                     │
│  ┌────┴────────────────────────────────────┐               │
│  │              │              │            │               │
│  ▼              ▼              ▼            ▼               │
│  Sub-Planner 1  Sub-Planner 2  ...  Sub-Planner N          │
│  (위임된 범위)   (위임된 범위)       (재귀적)                │
│       │              │                                      │
│  ┌────┴────┐    ┌────┴────┐                                │
│  ▼    ▼    ▼    ▼    ▼    ▼                                │
│  W1   W2   W3   W4   W5   W6    ← 각자 레포 복사본에서 작업 │
│       │              │                                      │
│       └──── Handoff ─┘                                      │
│       (결과 + 노트 + 우려사항 + 피드백)                      │
└─────────────────────────────────────────────────────────────┘
```

### 핵심 설계 원칙

| 역할 | 규칙 |
|------|------|
| **Root Planner** | 전체 범위 소유, 코딩 직접 안 함, 태스크 분배만 |
| **Sub-Planner** | 위임된 좁은 범위 완전 소유 (재귀적) |
| **Worker** | 태스크 완료에만 집중, 다른 에이전트와 소통 안 함, 자체 레포 복사본 |
| **Handoff** | 작업 내용 + 노트 + 우려사항 + 피드백 → Planner에게 반환 |

> "흥미롭게도, 이것은 실제 소프트웨어 팀이 오늘날 운영되는 방식과 유사하다"

### 5단계: Integrator 제거

```
Integrator (중앙 품질 관리) 추가 → 명백한 병목
수백 명의 Worker, 하나의 게이트 = "관료주의"
→ 제거하여 시스템 단순화
```

## 핵심 트레이드오프

### 1. 커밋 정확성 vs 처리량

```
100% 정확성 요구 시:
├── 작은 에러 하나 → 전체 시스템 정지
├── Worker가 범위 밖 수정 시작
├── 여러 에이전트가 같은 문제에 몰림
└── 처리량 급감

해결: 일정 오류율 허용
├── 다른 에이전트가 곧 수정할 것이라 신뢰
├── 오류율: 작고 일정 (폭발적 증가 X)
└── 최종 "green" 브랜치에서 fixup pass
```

### 2. 동기화 오버헤드

```
여러 에이전트가 같은 파일 수정 → 일시적 혼란 허용
→ 시스템이 자연스럽게 수렴
→ 추가 토큰 소모, but 전체 생산성 향상
```

## 프롬프트 엔지니어링 학습

### 핵심 원칙

| 원칙 | 설명 |
|------|------|
| **뛰어난 신입처럼 대하기** | 엔지니어링은 알지만 코드베이스/프로세스는 모름 |
| **제약 > 지시** | "TODO 금지" > "구현 완료하기" |
| **체크박스 사고 피하기** | 의도 전달, 구체적 목록은 범위 축소 유발 |
| **구체적 숫자 제시** | "많은 태스크" → 적게 생성 / "20-100개 태스크" → 의도대로 |

### 지시 실패 사례

| 실패 | 원인 | 해결 |
|------|------|------|
| 불필요한 기능에 깊이 빠짐 | "spec 구현" 지시가 너무 모호 | 우선순위 명시 |
| 성능 무시 | 암묵적 기대 | 명시적 타임아웃 강제 |
| 메모리 누수/데드락 | 에이전트가 자연스럽게 감지 못함 | 명시적 리소스 관리 도구 |
| 불필요한 의존성 | 금지 사항 미명시 | 의존성 철학 명시적 기재 |

## 시스템 설계 원칙

```
1. 안티프래질 (Anti-fragile)
   - 에이전트 수 증가 → 실패 확률 증가
   - 개별 에이전트 실패해도 시스템 유지
   - 다른 에이전트가 복구/대안 시도

2. 경험적 > 가정 기반 (Empirical)
   - 관찰과 데이터로 조정
   - 인간 조직이나 기존 설계 가정 배제

3. 처리량 우선 설계 (Design for throughput)
   - 일정 오류율 허용 → 최종 정리 패스
   - 100% 정확성 = 처리량 급감
```

## 핵심 포인트

1. **~1,000 커밋/시간**: 수천 에이전트가 1주일간 사람 개입 없이 브라우저 구현
2. **재귀적 Planner + Worker**: 실제 소프트웨어 팀 구조와 유사한 에이전트 패턴
3. **오류 허용**: 100% 정확성보다 처리량 우선, 최종 fixup 브랜치로 정리
4. **자율 수렴**: 파일 충돌/에러를 시스템이 자연스럽게 해결
5. **지시의 중요성**: 10배 컴퓨트 = 불명확한 지시도 10배 증폭
6. **제약 > 지시**: 모델은 기본적으로 좋은 일을 함, 경계만 정의
7. **프로젝트 구조 = 처리량**: 모놀리스 → 크레이트 분리 시 처리량 수배 향상
8. **선순환 루프**: AI로 AI를 개발, 모델/에이전트/하네스 개선이 서로 가속
